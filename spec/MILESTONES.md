# MILESTONES – אתר TODO List משותף

**מסמכי מקור:** `PRD.md`, `ARCHITECTURE.md`, `DESIGN.md`  
**מטרה:** חלוקת פיתוח האתר ל-Milestones ניתנים לבדיקה ולאישור, בדגש על Vertical Slices.

## כללי ביצוע הפיתוח – Development Execution Rules

1. יש לפתח את ה-Milestones **לפי הסדר** המופיע להלן. אין לדלג על אבן דרך או להתחיל אבן דרך מאוחרת טרם אישור קודמתה.
2. בסיום כל Milestone יש **לעצור את הפיתוח**, להציג למשתמש את התוצר העובד, לפרט אילו בדיקות בוצעו ולהציג את תוצאותיהן מול כל סעיף ב-**Definition of Done**. יש לציין במפורש כל בדיקה שלא בוצעה או כל תנאי שלא הושלם.
3. **אין להתחיל בפיתוח ה-Milestone הבא ללא אישור מפורש של המשתמש.** תיקונים הנדרשים לצורך עמידה ב-Definition of Done שייכים לאותה אבן דרך.
4. אין להוסיף פיצ'רים או לשנות את ה-PRD, ה-ARCHITECTURE או ה-DESIGN ללא אישור. כאשר יש סתירה בין דוגמאות חזותיות לבין הדרישות, יש לפעול לפי סדר הקדימויות שב-`DESIGN.md`.
5. כל Milestone יותיר את מה שכבר פותח במצב עובד וניתן לבדיקה; יש לבצע בדיקות רגרסיה מתאימות על היכולות הקודמות.
6. ה-**Definition of Done** כולל רק תנאים שאפשר לבדוק לפני הדחיפה, במחשב ומול פרויקט ה-Dev. תנאים שאפשר לבדוק רק באתר החי מופיעים בנפרד, תחת **לבדיקה אחרי הדחיפה**, ונבדקים מיד אחרי הדחיפה שמאשרת את ה-Milestone (ראו `CLAUDE.md`).

## Milestone 1 – האפליקציה רצה במחשב מול מסד ה-Dev

**שם ומטרה:** Slice ראשון מקצה לקצה שרץ במחשב הפיתוח: האפליקציה מציגה רשימת משימות מתוך מסד נתונים אמיתי (פרויקט ה-Dev), עם שני הדפים ותצוגת פרטי משימה. אין עדיין פריסה לאתר חי ואין שימוש בפרויקט Production.

**מה יש לממש:**
- פרויקט React + TypeScript + Vite, ניווט לשני הנתיבים `/` ו-`/about`, CSS בסיסי בעברית RTL, כולל פריסה Responsive: שני אזורים זה לצד זה בדסקטופ, ועמודה אחת (רשימה מעל פרטים) במובייל.
- פרויקט Supabase **Dev** בלבד, עם `tasks` ו-Constraints בהתאם ל-`ARCHITECTURE.md`, ומשתמש המסד `app_backend` לפי ADR-2. Database Migrations ב-Git, המוחלות על Dev באמצעות Supabase CLI המקושר ל-Dev בלבד. את יצירת הפרויקט ואת יצירת `app_backend` המשתמש מבצע בעצמו, בהדרכה צעד אחר צעד.
- קובץ נתוני בדיקה `supabase/dev-seed.sql`, ל-Dev בלבד, שאינו Migration ולעולם אינו מוחל על Production. הרצתו מחליפה את כל תוכן טבלת `tasks` ב-Dev בחמש המשימות מה-Wireframes, לפי הסדר הזה:
  1. **לקנות מצרכים** – ללא תיאור, ללא תאריך יעד, לביצוע.
  2. **לתכנן חופשה** – תיאור: "לבדוק יעדים, מחירים ולסגור טיסות"; תאריך יעד: שבוע מיום ההרצה; לביצוע.
  3. **לסיים דוח שנתי** – ללא תיאור, ללא תאריך יעד, **הושלמה**.
  4. **לפנות למוסך** – ללא תיאור, ללא תאריך יעד, לביצוע.
  5. **ללא כותרת** – תיאור ארוך שמתחיל ב-"לבדוק אפשרויות ביטוח לרכב" וארוך מספיק כדי להיקטע ברשימה; ללא תאריך יעד; לביצוע.
- Vercel Functions ב-Node.js/TypeScript, חיבור מאובטח דרך Pooler ו-`GET /api/tasks` שמחזיר נתונים לפי `position`.
- דף הבית עם Header וניווט, רשימת משימות בצד ימין ואזור פרטים בצד שמאל בדסקטופ; טקסט כותרת או תחילת תיאור מקוצרת, מצב רשימה ריקה, סימון חזותי למשימה שהושלמה, מצב טעינה ושגיאת רשת.
- בחירה של משימה והצגת ערכיה באזור הפרטים; בהיעדר בחירה: **"בחר משימה מהרשימה כדי לצפות בפרטיה"**. ניתן להציג שדות פרטים בהתאם לעיצוב, אך אין עדיין להציג פעולות כתיבה כאילו הן עובדות.
- דף אודות עם הסבר קצר ותפריט ניווט תואם.
- הרצה מקומית באמצעות `vercel dev` מול פרויקט ה-Dev, כולל SPA fallback כך ש-Refresh ב-`/about` עובד בלי לפגוע ב-`/api/*`; `.env.example` המתעד את שמות משתני הסביבה.

**תוצר מצופה:** האפליקציה רצה במחשב עם שני דפים, רשימה משותפת הנקראת מתוך PostgreSQL של Dev ותצוגת פרטי משימה נבחרת, על בסיס נתוני הבדיקה. אין עדיין ממשק יצירת משימה ואין אתר חי.

**Definition of Done:**
- [ ] `GET /api/tasks` מחזיר משימות ממסד הנתונים בסדר קבוע; רשימה ריקה מחזירה `[]`.
- [ ] הרצת `supabase/dev-seed.sql` על Dev מציגה בדף הבית את חמש המשימות לפי הסדר; הרצה חוזרת מחזירה את הרשימה בדיוק לאותו מצב.
- [ ] דף הבית מציג כותרת או תיאור מקוצר במקרה שאין כותרת; משימה שהושלמה מובחנת חזותית.
- [ ] בעת כניסה אין משימה נבחרת; בחירת שורה מציגה את פרטיה; שגיאת טעינה אינה מוצגת בטעות כרשימה ריקה.
- [ ] מעבר בין **דף הבית** ל-**אודות**, כולל Refresh ב-`/about`, פועל.
- [ ] מבנה המסכים תואם את ה-Wireframes בדסקטופ ובמובייל (רשימה מעל פרטים במסך צר), עם צבעי הבסיס והגופנים מה-Style Guide; הליטוש החזותי המלא שייך ל-Milestone 6.
- [ ] לאחר שינוי נתוני בדיקה במסד, Refresh בדפדפן מחזיר את הרשימה העדכנית; הנתונים אינם מאוחסנים ב-Local Storage.
- [ ] פרטי חיבור ל-Database אינם נחשפים בקוד לקוח או ב-Git; Migrations מתועדות, הוחלו על פרויקט ה-Dev באמצעות ה-CLI, וניתנות להרצה מחדש על פרויקט ה-Dev.
- [ ] האתר רץ מקומית מול פרויקט ה-Dev בלבד; לא נוצר ולא נעשה שימוש בפרויקט Production.

## Milestone 2 – פריסה לאתר חי

**שם ומטרה:** להעלות את מה שנבנה ב-Milestone 1 לאתר ציבורי ב-HTTPS, עם מסד Production נפרד, כך שמכאן והלאה כל דחיפה לגיטהאב מעדכנת את האתר החי ואת מבנה מסד הנתונים שלו אוטומטית. אין באבן דרך זו פיצ'רים חדשים.

**מה יש לממש:**
- פרויקט Supabase **Production**, עם משתמש `app_backend` וסיסמה נפרדת משל Dev, וה-Data API כבוי (ADR-2). `app_backend` חייב להיווצר ב-Production **לפני** הדחיפה, כי ה-Migrations מעניקות לו הרשאות.
- חיבור פרויקט ה-Production ל-Repository דרך Supabase GitHub Integration עם *Deploy to production* (ADR-1). פרויקט ה-Dev אינו מחובר ל-GitHub.
- פרויקט Vercel המחובר ל-Repository, עם Build/Deployment אוטומטי בכל Push לענף הראשי. משתני סביבה נפרדים לכל סביבה: Production מחובר למסד ה-Production; Preview ו-Development מחוברים למסד ה-Dev בלבד.
- הגדרות Build ו-Routing לפריסה: SPA fallback שאינו פוגע ב-`/api/*`, בקבצים סטטיים או ב-Manifest.
- את פתיחת החשבונות, יצירת הפרויקטים והזנת הסיסמאות ומשתני הסביבה המשתמש מבצע בעצמו; Claude מכין את מה שנדרש בקוד ומדריך צעד אחר צעד בשפה פשוטה.

**תוצר מצופה:** הכול מוכן לפריסה, וכל ההגדרות בחשבונות הושלמו. האתר החי עולה בדחיפה שמאשרת את אבן הדרך, ונבדק מיד אחריה.

**Definition of Done:**
- [ ] Build של הפרויקט עובר במחשב ללא שגיאות.
- [ ] הגדרות ה-Routing לפריסה קיימות, וב-`vercel dev` עדיין: Refresh ב-`/about` עובד ו-`/api/tasks` מחזיר JSON.
- [ ] פרויקט ה-Production קיים, `app_backend` נוצר בו וה-Data API כבוי (המשתמש מאשר שביצע לפי ההדרכה).
- [ ] Supabase GitHub Integration מוגדר לפרויקט ה-Production בלבד, עם *Deploy to production*.
- [ ] פרויקט Vercel מחובר ל-Repository; משתני הסביבה של Production מצביעים על מסד ה-Production, ושל Preview ו-Development על מסד ה-Dev.
- [ ] פרטי חיבור ל-Database אינם ב-Git ואינם בקוד הלקוח; כל ה-Migrations תואמות-לאחור ואינן הרסניות.
- [ ] כל הבדיקות של Milestone 1 עדיין עוברות במחשב.

**לבדיקה אחרי הדחיפה:**
- [ ] ה-Deployment ב-Vercel הצליח, והאתר החי נטען ב-HTTPS.
- [ ] ה-Migrations הוחלו על Production אוטומטית, ללא פעולה ידנית; באתר החי מוצגת רשימה ריקה, ללא נתוני הבדיקה של Dev.
- [ ] באתר החי: מעבר בין **דף הבית** ל-**אודות** ו-Refresh ב-`/about` עובדים; `/api/tasks` מחזיר JSON ולא את דף האפליקציה.
- [ ] בדיקה ראשונית של טעינה וניווט עוברת ב-Chrome במחשב וב-Chrome ב-Android.

## Milestone 3 – יצירת משימה באמצעות Modal

**שם ומטרה:** לאפשר לכל מבקר להוסיף משימה לרשימה המשותפת מקצה לקצה, באמצעות ממשק תקין ו-Validation.

**מה יש לממש:**
- כפתור **"הוסף משימה"** ו-Modal בעברית לפי `DESIGN.md`, כולל שדות כותרת, תיאור ותאריך יעד ו-Placeholders.
- ערכי פתיחה: כותרת ותיאור ריקים, תאריך יעד הוא היום המקומי וניתן לנקותו. אין שדה לבחירת סטטוס: משימה חדשה מתחילה כ"לביצוע".
- Validation בצד לקוח ובשרת: לפחות כותרת או תיאור לא ריקים אחרי `trim`, גבולות 100/2000 תווים, תאריך יעד תקין שהוא היום או בעתיד, או `null`.
- `POST /api/tasks` עם SQL פרמטרי והוספה אטומית בסוף הרשימה, כולל כללי הנעילה המשותפת לפעולות המשנות את מבנה הרשימה.
- תקרת 1,000 משימות: בשרת, בדיקה בתוך ה-Transaction של היצירה ותשובת `409` כשהרשימה מלאה; בלקוח, כפתור **"הוסף משימה"** במצב Disabled עם הודעה כשברשימה 1,000 משימות.
- סגירה ללא שמירה מבטלת את הטיוטה ללא התראה; שמירה מוצלחת סוגרת Modal, מעדכנת רשימה ובוחרת את המשימה החדשה. בשגיאה נשארים הנתונים והודעת השגיאה מופיעה בטופס.

**תוצר מצופה:** משתמש יכול להוסיף משימה דרך האתר והיא מופיעה בסוף הרשימה המשותפת ונשמרת לאורך Refresh.

**Definition of Done:**
- [ ] אפשר ליצור משימה עם כותרת בלבד, עם תיאור בלבד, או עם שניהם; תאריך יעד אופציונלי.
- [ ] שדות ריקים/רווחים בלבד, חריגה ממגבלות אורך ותאריך יעד בעבר נחסמים עם הודעת Validation בתוך הטופס.
- [ ] התאריך הראשוני הוא היום, ניתן לנקותו, ואין בחירת שעה.
- [ ] שמירה מוצלחת יוצרת **רשומה אחת** במסד, בסטטוס "לביצוע", מציגה אותה ברשימה, סוגרת Modal ובוחרת אותה כך שפרטיה מוצגים.
- [ ] כשברשימה 1,000 משימות, הכפתור אינו זמין ומוצגת הודעה; בקשת יצירה ישירה ל-API נדחית ב-`409` ואינה יוצרת רשומה, גם בשתי בקשות מקבילות.
- [ ] סגירה ופתיחה מחדש ללא שמירה מאפסות את הטופס; שגיאת שרת משאירה Modal וערכים ומאפשרת ניסיון חוזר.
- [ ] הנתונים נראים ב-Chrome גם לאחר Refresh ובחלון דפדפן נוסף; כל הבדיקות הקודמות עדיין עוברות.

**לבדיקה אחרי הדחיפה:**
- [ ] באתר החי: משימה שנוצרה במחשב מופיעה גם ב-Chrome ב-Android לאחר Refresh.

## Milestone 4 – עריכת פרטים ומחיקת משימה

**שם ומטרה:** להשלים ניהול משימה נבחרת, כולל Inline Edit ושמירה מפורשת ומחיקה עם אישור.

**מה יש לממש:**
- אזור פרטי משימה המציג מיד שדות **כותרת**, **תיאור** ו-**תאריך יעד** ניתנים לעריכה; לחצני **"שמור שינויים"** ו-**"מחק משימה"**.
- `PATCH /api/tasks/:id` לעדכון שלושת שדות הפרטים בלבד (לא `completed` או `position`); Validation כמו ביצירה, אלא שהכלל "תאריך יעד לא יכול להיות בעבר" חל רק כאשר התאריך שונה מהערך השמור.
- טיוטת עריכה בזיכרון בלבד; מעבר למשימה אחרת, מעבר דף או Refresh מבטלים שינויים שלא נשמרו ללא התראה.
- Modal אישור מחיקה לפי `DESIGN.md`, `DELETE /api/tasks/:id`, ואיפוס אזור הפרטים לאחר הצלחה.
- טיפול בכשלים בכתיבה, במשימה שנמחקה בינתיים (`404`) ובכלל `last write wins` בעדכון פרטים; אין מנגנון פתרון התנגשויות.

**תוצר מצופה:** ניתן לבחור משימה, לשנות ולשמור פרטיה, לבטל שינויים באמצעות מעבר ללא שמירה, ולמחוק אותה לאחר אישור.

**Definition of Done:**
- [ ] עריכת כותרת/תיאור/תאריך ושמירה שומרות ב-Database ורואים את התוצאה לאחר Refresh.
- [ ] משימה שתאריך היעד השמור שלה כבר עבר ניתנת לעריכה ולשמירה בלי לשנות את התאריך; שינוי התאריך לתאריך אחר בעבר נחסם.
- [ ] בחירה במשימה אחרת, מעבר לאודות או Refresh ללא שמירה מבטלים את הטיוטה ללא התראה.
- [ ] כישלון שמירה או Validation לא תקין מציגים שגיאה ומשאירים את תוכן העריכה ללא שינוי.
- [ ] לחיצה על **"מחק משימה"** פותחת אישור; **"ביטול"** משאיר אותה; **"אישור"** מוחק רק לאחר הצלחת השרת.
- [ ] לאחר מחיקה מוצלחת המשימה נעלמת ואזור הפרטים חוזר להודעת הבחירה; כישלון מחיקה אינו מסיר אותה מהתצוגה כאילו נמחקה.
- [ ] בבדיקה של שמירות מקבילות לפרטי אותה משימה השמירה האחרונה בשרת קובעת; אין דריסה עקיפה של סטטוס או סדר.
- [ ] מראה השדות וה-Modal תואם את `DESIGN.md`, ובדיקות ה-Milestones הקודמים עוברות.

## Milestone 5 – סטטוס ביצוע וסדר ידני

**שם ומטרה:** להשלים ניהול הרשימה המשותפת באמצעות Checkbox ו-Drag & Drop, כולל שמירת סדר עקבית בין מבקרים.

**מה יש לממש:**
- Checkbox בכל שורה; `PATCH /api/tasks/:id/status` ששומר מיד את הערך המפורש ומאפשר גם החזרה מ"הושלמה" ל"לביצוע".
- טקסט חצוי/סימון מתאים למשימות שהושלמו, בלי להזיז אותן או לחלק את הרשימה לקבוצות.
- סימון השלמה או גרירה של המשימה הנבחרת אינם מאפסים ואינם שומרים שינויים שלא נשמרו באזור הפרטים.
- Drag Handle ו-`dnd-kit` לסידור שורות בעכבר ובמגע ב-Android; `PUT /api/tasks/order` עם רשימת המזהים השלמה.
- Transactions, Advisory Lock משותף, נרמול `position` ואימות קבוצת המזהים למניעת אובדן או כפילות בעת יצירה/מחיקה/גרירה במקביל.
- טיפול בכישלון שינוי סטטוס או סדר: החזרת ה-UI לערך הידוע האחרון והודעה מתאימה. במקרה של `409` אין לדרוס את הרשימה; מוצגת אפשרות לרענן.
- שמירת מצב תצוגה ללא Polling/Real-Time: פעולות מבקר אחר נראות לאחר כניסה מחדש לדף הבית או Refresh.

**תוצר מצופה:** רשימה יחידה שניתן לסמן ולסדר ידנית בדסקטופ ובמובייל; כל השינויים נשמרים במסד הנתונים לכל המבקרים.
